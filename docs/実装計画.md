# CardQuest 実装計画（v0.8.0 → v1.0）

現状：v0.8.0。盤面レイアウト・チャネリング操作・押し込み・持ち主/操作権/情報公開の表示までが
`js/layout.js`（約700行）に実装済み。戦闘処理・カード効果・AI・ラン・メタはすべて未着手。
カードマスター169種は `js/data.js` に取り込み済み。

## 方針

1. **エンジンとUIを分離する。** いまの `layout.js` はUIプロトタイプとして優秀だが、
   ゲームルールがDOM操作と混ざり始めている。ルールを純粋な状態遷移モジュール
   （`js/engine/`、DOM非依存・Node単体で動く）に移し、`layout.js` は描画と入力に専念させる。
   これで**ルールの自動テストが可能**になり、能力値計算・カード効果169種の検証が現実的になる。
2. **各マイルストーンで「遊べる状態」を保つ。** 仕様書§15の推奨手順（盤面→能力値→ターン→戦闘→
   効果→AI→外側）に沿い、毎版タブレットで触れる形でリリースする。
3. **乱数はすべてシード付きRNG経由。** 最初に入れる（後から入れるのは困難）。
4. カード効果は**データ駆動のディスパッチャ**（idごとの関数テーブル）にし、
   1枚実装するごとに単体テストを1本書く。

## モジュール構成（目標）

```
js/
  engine/
    rng.js        シード付き乱数
    state.js      Battle/Master/Lane データ構造・シリアライズ
    stats.js      能力値計算（仕様書§6の順序をそのまま関数化）
    turn.js       ドロー・配置・メイン・ターン終了
    combat.js     アタック解決（§7）・破壊・LPダメージ・戦利品判定
    effects/
      skills.js   技能カード＝集計変数方式（§9）
      magic.js    魔法48種ディスパッチャ（§8）
      units.js    ユニット固有能力（§10、A→C→B→Dの順）
    ai.js         敵AI（§11の評価関数移植）
  run/
    map.js        分岐マップ生成（confquest genMap 移植）
    nodes.js      マスのイベント処理・報酬
    areas.js      エリア定義（敵プール・ドロップ表・ボス）
  meta/
    save.js       cq_* localStorage・バックアップ

  data.js  opponents.js  layout.js  version.js  update.js

  sync-version.js  simulate.js（ヘッドレス対戦・ラン統計）

```

## マイルストーン

### M1（v0.9）エンジン基盤と能力値計算 — 最重要・最初の山

- `engine/state.js`：仕様書§2.1のデータ構造。現行 `layout.js` の `mine/foes` 配列から移行
- `engine/rng.js`：シード付き乱数
- `engine/stats.js`：**§6.2の適用順序を1関数ずつ忠実に**（突然変異→CHボーナス→磁場変動の順、
  クランプなし、負値許容）。技能の集計はまず主要10種（狂戦士化・五つ星・膨張・迎撃・貫通・
  甲殻・気化・石化・封印・増幅）
- テスト：仕様書の計算例＋境界ケース（黒の邪霊陣＋疫障で負値になる等）をNodeで自動検証
- UI：カードの表示A/D値をエンジン計算値に接続

**この段階を厚くやる。** ここが正しくないと以降の全検証が無意味（仕様書§15の警告どおり）。

### M2（v0.10）ターン進行と対人ルール完成

- `engine/turn.js`：ドロー（残枚数テーブル方式）・手札7枚強制捨て・配置/メインステップの区別
  （押し込みは配置のみ等）・硬直・リバースポインタ（下から上への一方通行、クローズは技能のみ）・
  ターン終了処理（硬直解除・表向き魔法消滅・未行動ドロー）
- チェンジ（毎バトル1回・LP1）
- 勝敗判定（LP0・山札切れ）
- この時点で「効果なしカードだけの2人打ち」が成立（同一端末で交互操作のデバッグモード）

### M3（v0.11）戦闘（アタック）

## 各工程で使うClaudeモデルの推奨

使い分けの原則：**「仕様書に答えが書いてある作業」はSonnet、「判断・設計・原因究明」はFable/Opus、
「機械的な繰り返し」はHaiku。** 上位モデルほど使用量を速く消費するので、
物量のM4・M6〜M7をSonnetで流せる状態（＝仕様とテストの整備）を上位モデルで先に作るのが最も効率的。

| 工程 | 推奨モデル | 理由 |
|---|---|---|
| M1 エンジン基盤・能力値計算 | **Fable**（最低でもOpus） | 全工程で最も間違えてはいけない場所。§6.2の適用順序の忠実な翻訳、エンジン/UI分離のアーキテクチャ決定、テスト設計まで一気に固める。ここの品質が以降の全コストを決める |
| M2 ターン進行 | **Sonnet** | 仕様書02に手順が完全に文書化済み。素直な状態機械の実装で、M1のテスト基盤に乗せるだけ |
| M3 戦闘（アタック） | **Opus** | 迎撃・反射・貫通・不死・通常攻撃フラグ(SW550)など分岐が多く、対話UIとの絡みもある。仕様はあるが組み合わせの検証に判断力が要る |
| M4 カード効果169種 | **Sonnet**で量産＋**Fable/Opus**で難物 | 大半は「仕様書の該当行→関数1つ＋テスト1本」のパターン作業。ただし傀儡・憑依・身転換・連唱・摩り替り・魂の門など状態をまたぐ約15枚はOpus以上で実装またはレビュー |
| M5 敵AI | **Fable**（最低でもOpus） | 評価関数の移植自体より「原作らしく振る舞っているか」の検証・デバッグが重い。シミュレータの結果を読んで挙動を診断する仕事 |
| M6 ラン（分岐マップ） | **Sonnet** | confquestからの移植が主体。設計判断は仕様書側で済んでいる |
| M7 メタ（ホーム・収集・ショップ） | **Sonnet**（軽微な調整はHaiku） | 定型的な画面実装とlocalStorage処理 |
| M8 コンテンツ展開・バランス | 実装は**Sonnet**／バランス分析は**Opus** | エリア追加・データ抽出は定型。シミュレーション結果から§7の数値を決める分析だけ上位モデルで |
| M9 仕上げ | **Sonnet**（文言・CHANGELOG・リリース作業はHaiku） | 演出・チュートリアルは通常実装。sync-version〜pushの定型作業に上位モデルは不要 |

工程をまたぐ使い分け：

- **仕様の変更・設計の相談・原因不明のバグ調査**は工程を問わずFableに切り替える。
  特に「テストは通るのに実機で挙動がおかしい」類はエンジン/UI境界の設計問題であることが多い
- **リリース作業・CHANGELOG執筆・コメント整理・軽微なCSS調整**はHaikuで十分
- テストコードは実装と同じモデルで同時に書かせる（後から別モデルに書かせると仕様解釈がずれる）

## リスクと対策

| リスク | 対策 |
|---|---|
| 能力値計算の順序ミス（発見が遅れると全部に波及） | M1で仕様書§6.2を1行ずつ関数化し、テストを先に書く。UIより先にエンジン |
| カード効果169種の物量 | データ駆動＋1枚1テスト＋シミュレータの総当たり。版を3つに分割 |
| 原作AIの複雑さ | 評価関数と閾値は仕様書§11.2に数値まで書いてある。まず忠実移植し、調整はパラメータで |
| `layout.js` の肥大化 | M1でエンジン分離。以降 `layout.js` には状態を持たせない |
| 敵デッキデータが未抽出 | M8で必要。`CardBattle仕様書/09_setup_decks.md` を先にプロジェクトに取り込んでおくと安全 |

## 検証の仕組み（各版共通）

1. `node tests/run.js` — エンジン単体テスト（CI代わりにコミット前必須）
2. `node tools/simulate.js` — ヘッドレス対戦・ラン踏破統計（confquestの3000ラン検証と同じ手法）
3. 実機（Galaxy Tab S11）確認 → `sync-version.js` → push → タブレットで「更新」
